SentryC2

Lose the network. Keep the robot — and the ability to stop it.

SentryC2 is a research project on edge-delegated authorization for industrial robots in disconnected environments: keeping work running through a network outage without giving up a trustworthy, physically enforced stop.

Work in progress — active thesis research, 2026

The problem

In standard Industry 4.0 deployments, a robot's permission to operate is a lease issued by a cloud identity provider. Sever the network and the lease expires — the robot halts, not because anything became unsafe, but because permission timed out in a datacenter it can no longer reach. In disconnected, intermittent, or limited environments — remote sites, forward-deployed logistics, or a plain ISP failure — that coupling turns every network fault into production downtime.

Moving authorization to the edge creates the opposite problem, and it is the harder one: once no external authority can revoke permission, the edge must be able to revoke it itself — and enforce that revocation physically. That inversion is what this project investigates.

How it works

An edge node beside the robot verifies cryptographic evidence every cycle and maintains a trust score. Under attack — or when verification degrades — the score decays step by step. When it crosses a threshold, the node revokes authorization and a hardware intercept halts the robot through its safeguard inputs. Stop latency is the number of decay cycles multiplied by the cycle time, which is what makes it predictable.

What was built

A physical prototype, not a simulation: a live Universal Robots UR5, an edge stack of a supervisor and two microcontroller nodes, and an opto-isolated 24 V intercept wired into the robot's safeguard inputs — active-high, so losing the edge node's power fails to the stopped state. The trust decision runs on the edge node and reaches the robot with no network round-trip and no software stop path.

This is a research prototype for studying authorization latency — not a certified functional safety system.

Findings so far

Physical trial campaigns on the live UR5 support three qualitative conclusions. Quantitative detail is withheld while the thesis is in progress.

  • Verification cost delays the stop.

    Heavier cryptographic verification per cycle arrives at the halt measurably later — and the relationship follows a simple model, predictable enough to design against.

  • Outage duration decides whether a stop occurs.

    Short outages ride through on residual trust; outages that outlast the decay boundary end in a physical stop, right where the model places the line.

  • Stronger proofs price into stop latency.

    Privacy-preserving verification is affordable for continuity, but it delays the stop — a trade the model prices explicitly.
